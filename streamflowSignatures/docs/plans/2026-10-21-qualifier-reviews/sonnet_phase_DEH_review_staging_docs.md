## Findings

### BLOCKER
None that invalidate the data. The numbers I recomputed all hold. The items below should be fixed before upload because a data user reads them first.

### MAJOR
1. **R2 README lists a file that is not shipped.** `resource2.../hisss_readme_wy1980_2025.md:37` has `hisss_run_log_wy1980_2025.log | Console log of the production run`; no such file is in the folder or in the rename manifest (R1's README has no such row). It is a leftover of the v2 README (`Signatures_v2_12oct2026/.../readme:30`). `check` passes 21/21 because REQUIRED does not parse the README. Fix: drop the row or ship the log; add a README-vs-folder check.
2. **Run notes contain a placeholder "?"**: `hisss_run_notes_wy1993_2025.md` "Independent recomputation of the 1609 changed gages ... annual key sets identical, ? values beyond 1e-9" (same in R2). Cause: `stage_hydroshare_qualifier_v3.py` reads `e7a.get('n_value_diff', e7a.get('over_tolerance','?'))`, but `e7_annual.json` has neither key (it has `allow_value_diff`: 117 / 188; the text file says over-tolerance=117 / 188). A silent '?' default is the exact "typed or defaulted number" defect; the tool should fail on a missing key.
3. **Shipped data dictionary contradicts the README on `flagged_for_high_na`.** All three copies (top level, R1, R2; identical to the v2 staging, `hisss_data_dictionary.csv:2272`) still say "KNOWN ISSUE ... computed over the 16 numeric metadata columns only ... Do not use it to screen gages ... will be regenerated the next time any portion of the data is rerun". The v3 data carry the corrected flag (I recomputed it: 471 / 345 TRUE, 0 mismatches), and the README says "regenerated in this version". STATUS itself says the dictionary row is to be updated with the version-2 deposit; the staging did not do it. A user following the dictionary would discard a valid flag.
4. **Naming: public "version 2" vs internal "v3" leaks into shipped files.** The README heading says "version 2"; the explorers' title is "HISSS signatures WY ... (version 3: qualifier mask + climate frame fixed) - 26 Oct 2026" (`"meta":{"title"` in both HTML files, `generated 2026-10-28`); the census/gates files are titled "Change census v3_vs_v2" and the gates JSON has `"label": "v3_vs_v2"`; run notes say "(internal build v3)". The "previous build" these documents compare against (the 12-13 Oct version-2 build) was never deposited and is not on HydroShare, so "v2" in the census files points at something users cannot get - and a user will read "v2" as the 2026 delivery (1,653 columns), which is a different object. README/notes should say once, plainly: "previous build = unpublished internal build; the 2026 deposit is the version-1 resource". Rebuild the explorer title or accept and document it.
5. **Understated port-check sentence (README run notes, python/README.md:263-266, CHANGELOG, plan).** Run notes: "summary table cell for cell within 1e-6 except the named near-zero-tail rank statistics and `ice_affected_days_total`". The port-check file itself reports: worst relative difference 2.0 (D10_day_linear_slp), 1,510 / 2,503 tie-bearing rank statistics and 472 / 775 propagated residuals that are NOT within 1e-6 but are accepted after recomputation from each side's own annual series, 103 waived columns (ice + FDCmid/FDC90th Pettitt/MK/Spearman), 15 / 18 signed-zero ties and 8 / 7 gate-state cells (NaN in one language, finite in the other, e.g. FDC90th_mk_pval gage 15896000 NaN in Julia, 0.128 in Python; FDC90th_pettitt_pct_change 02304500 100 vs NaN). `python/README.md:265-266` ("every summary cell within 1e-6 except the named FDC90th / FDCmid near-zero-tail class") is worse: it omits the ice column, the ties and the gate-state cells. CROSS_LANGUAGE_STATUS.md:47-65 states it correctly; copy that wording. Also relevant to a data user: the 8 / 7 gate-state cells mean the Julia product has a trend field NaN where the independent port computes a value (or the reverse) on 4 gages (15896000, 02304500, 02313230, 401733105392404); this is not mentioned in any shipped README.

## Direct answers
- **D, numbers:** every count in the three READMEs, both run notes, the abstracts and the dictionary that I could recompute is right except the "~588,000 NA rows" (stale) and the "?" in the run notes. Hashes match across notes, manifest, provenance and the data.
- **D, misleading for a user:** (i) "version 2" public vs "version 3" in the explorers/census and the unreachable "previous build"; (ii) the stale `flagged_for_high_na` dictionary row; (iii) the port-check sentence that overstates agreement and hides the 8 / 7 NaN-vs-value cells; (iv) `flag` keeps the February code on restored days (stated in R3 README, fine, but 96 days are provisional today); (v) the metadata is updated in place (R3 README states this and ships the February copy plus the change list - adequate; the dictionary row for the change list is wrong).
- **Recipe contract:** holds as a verifier; the shipped docs should call it a "verification recipe" or add an option to write the reconstructed table.
- **Staging tool:** README anchors fail loudly (`must_replace` raises SystemExit when the anchor count is not 1) - good; the silent '?' defaults and the missing README-vs-folder check are the defects.
