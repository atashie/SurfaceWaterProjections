## 1. Findings

### 1. MINOR (documentation) — the interpolated Dec 31 of leap calendar years is a fabricated day in every precipitation and temperature series

- **Where:** `julia/src/io.jl:445-504` (PPT gap fill) and `:567-597` (TMIN/TMAX gap fill); consumed by every sum, count and run in `julia/src/climate.jl:269-355`.
- **Spec/decision:** Daymet has no Dec 31 in leap calendar years; the brief says the preprocessor interpolates the one-day hole. The metrics are defined on daily P (and tmin/tmax).
- **Code:** the hole is a one-day internal gap, so P(Dec 31) = (P(Dec 30) + P(Jan 1))/2 enters `prcp_annual`, `prcp_win`, 5-day windows, wet-day counts, dry-run detection, the 50 % and centre-of-mass timing, sd, Gini and the seasonality index; for temperature it enters `temp_*_win` and `gdd_cum_win/annual`. Water years affected: WY 1981, 85, ..., 2025 (12 of the 45 climate-valid WYs of the 1980–2025 product, 9 of 33 for 1993–2025).
- **Repro (real data, gage 01031450, WY 2001, input = batch-1 climate parquet):** raw rows for 2000-12-30 / 2000-12-31 / 2001-01-01 = 12.302 / **absent** / 0.000 mm; cleaned dowy 91, 92, 93 = 12.302, 6.151, 0.000. Over the 480 leap-hole gage-years of 40 batch-1 gages the invented day is on average 0.246 % of the annual total (median 0.105 %, max 2.1 % = 23.7 mm) and exceeds 10 mm in 24 of 480 (5 %), so `prcp_ndays_abv_10mm` counts a day nobody observed. Sensitivity of the 480 gage-years to the alternative "Dec 31 := 0": `prcp_50_dowy` changes in 66, `prcp_ndays_abv_10mm` in 24; to "Dec 31 := max of the two neighbours": `prcp_ndays_abv_10mm` in 74, `_25mm` in 4, `prcp_5d_max` in 2. `prcp_intermit_annual`, `prcp_1d_max`, `prcp_max_dowy` never change.
- **Fix:** no code change (same convention as the Q-to-PPT families and SWE; `docs/SIGNATURES.md` §12 says so for snow). `docs/SIGNATURES.md` §14 now has a caveat ("a day count such as `prcp_ndays_abv_10mm` can include one synthetic value in a leap year") that is too narrow and slightly wrong: (i) the affected water years are the ones that follow a leap calendar year (WY 2001, 2005, ...), not the leap water years that contain Feb 29 (WY 2000, 2004, ...), whose Dec 31 is not missing; (ii) every precipitation total, `prcp_50_dowy`, `prcp_cm_dowy`, sd, Gini, SI and, for temperature, `temp_*_win` and `gdd_cum_win/annual` are touched, not only the day counts; (iii) the size (mean 0.25 %, max 2.1 % of the annual total) is worth one line. Carry the corrected wording into the data dictionary and the HydroShare READMEs.

### 2. MINOR (RESOLVED in revision 2) — "ties take the first occurrence" failed when tied extremes differed only in the sign of zero

- **Where (12:19:17 revision):** `climate.jl` `argmax(P)`, `argmax(TX)`, `argmin(TN)`. Julia's `argmax/argmin` order −0.0 below +0.0; NumPy and R treat them as tied, so Julia would have disagreed with the ports.
- **Repro (12:19:17):** WY 2001, `TN = fill(5.0,365); TN[41] = 0.0; TN[61] = -0.0` gave `temp_min_annual_dowy = 61` (expected 41) and `temp_min_annual = -0.0`.
- **Revision 2:** `climate.jl:270` and `:434-435` add `.+ 0.0`; the same repro now returns 41 and +0.0, and a 3,000-year fuzz with signed zeros allowed in the inputs shows 0 mismatches. Practical impact was nil anyway: the 134,538,270 input rows contain no signed zero and no exact-zero tmin/tmax.
- **Remaining:** no test pins it (see 3e).

### 3. MINOR (tests) — the suite does not pin several things it appears to

`julia/test/test_climate_metrics.jl` (355 tests, all pass; file last changed 12:19:17).

- (a) **Leap-year frost cut-off.** `climate.jl:472-475` (Jun 30 = dowy 273 in a non-leap WY, 274 in a leap WY) is tested only in non-leap WY 2001. A constant `273` would pass all 355 tests and be wrong in leap WYs. My check: frost on dowy 274 and 275 of WY 2000 → `frost_last_dowy` = 274 (correct today); WY 2001 with 273/274 → 273.
- (b) **Gap fill.** The preprocessor test (`TN[100:101] .= NaN` on a constant −15 series, `@test y2002.TMIN[100] == -15.0`) cannot distinguish linear interpolation from "copy the left value". Use a ramp. (My 600-frame fuzz showed the formula is right.)
- (c) **Float64 `water_year`.** Every test frame comes from `add_water_year_columns` (Int). Production frames carry Float64 (`preprocess_daily_data` takes `yr` from the Float64 streamflow column), so `Int(yr)`, `Date(yr - 1, ...)` and `Dates.daysinmonth(cal_year, ...)` run on Float64 in production only. It works (verified on 2.1 M real values) but is unpinned.
- (d) **Record-anchored gate.** One scenario (0 of 10 frost years in the last decade). Not pinned: the exact 80 % boundary (8/10 passes, 7/10 skips), anchor-year denominators when some years are not anchors, span < 10 → no gate. (My 20,000 random cases are identical to a transcription of the `snow.jl` gate.)
- (e) **Revision-2 behaviours have no Julia test:** signed-zero normalisation, ±Inf rows → NaN year, the `%g` threshold labels (`12p5`, `1em05`; the Python suite tests the label function, the Julia suite does not), the duplicate-column-name guard, the temperature-policy validation.
- (f) The "equal blocks" regression test (0.1 mm × 50 twice) pins one pattern; its claim "whatever the rounding of 0.1 sums" is false in general (finding 4).

### 4. NOTE — `prcp_50_dowy` at an exact floating-point tie is decided by the last bit; the sequential-sum change does not remove that

- **Where:** `climate.jl:304-314` (`cum = _seqcumsum(P)`, `findfirst(c -> c >= frac * total, cum)`); the code comment already says so.
- **Repro (minimal, revision 2):** WY 2001, zeros except `P[10:12] = [1.1, 2.0, 0.7]` and the same three values again at `P[200:202]`. Exactly half of 7.6 mm is reached at the end of the first block (dowy 12); implementation returns **200**. Also `[1.9, 2.9, 1.9, 1.0]` (exact 13, returns 200) and `[0.9, 1.0, 2.6, 0.3]` (13, 200). `fill(0.1, 366)` in WY 2000 (exact tie at day 183) returns 184; `fill(0.3, 366)` returns 183. In 200,000 random years quantised to 0.1 mm, 1,624 have an exact tie and the current rule mis-decides 303 (19 %); the error can be as large as the dry gap between two equal blocks.
- **Impact on production: none.** In all 360,585 complete water years of the 8 input batches the smallest relative margin |cum_k − Σ/2|/Σ is 1.29e-9 (rounding noise is ~1e-15); nothing is closer than 1e-9.
- **Documented:** `docs/SIGNATURES.md` §14 says the tie "is decided by the last bit of the sequential sum" and is "identical across languages" (I did not check the ports). The documented caveat understates the size: the error is not one day but the whole dry gap between the two crossing candidates (188 days in the repro above).
- **Optional hardening (exact-decimal semantics instead of last-bit semantics):** `c >= frac * total * (1 - 1e-12)`. In my 200,000-year test it reproduces the decimal-exact day in all 1,624 tie years and changes no other year. If adopted, the same constant must go into the Python and R ports.

### 5. NOTE — three different non-finite policies

- **Where:** `io.jl:580` (TMIN/TMAX: ±Inf = missing), PPT/SWE blocks `io.jl:445-565` (only NaN = missing), `climate.jl:275/439` (any non-finite value → whole year NaN).
- **Repro:** one Inf day in PPT (WY 2001), SWE (WY 2002) and TMIN (WY 2003): `valid_climate_years = valid_swe_years = [2001,2002,2003]` (Inf accepted, year stays valid), `valid_temp_years = [2001,2002,2003]` with the Inf day replaced by its interpolation. Then `prcp_*` is NaN for WY 2001 while the Q-to-PPT families would ingest the Inf.
- **Impact:** none now; all 134.5 M input rows are finite (prcp ≤ 436.6 mm, tmin ≥ −58.4 °C, tmax ≤ 47.5 °C, tmin ≤ tmax everywhere). "Mirrors the PPT/SWE policy" (config comment, `io.jl`) and the `docs/SIGNATURES.md` §14 sentence "the PPT/SWE rules (... non-finite values count as missing)" are not literally true: PPT and SWE do not treat ±Inf as missing. Either extend `!isfinite` to PPT/SWE or reword the two sentences.

### 7. NOTE — where the co-authors' literal text and the binding decisions differ (for the relay list; none is a code defect)

- `prcp_annual_sd` / `_cv`: text says "standard deviation / coefficient of variability **for annual precipitation**"; decision 8 = within-year spread of the daily values. The plain reading would be an across-year scalar.
- `GDD_cum_*`: text `GDD = Σ((Tmax+Tmin)/2)` has no base and no clamp; decision 5 = base 0 °C, clamped. (The published page still lacks the base, per the brief.)
- `prcp_gini`: text says 1 = all rain on one day; the specified formula gives (n−1)/n = 0.99726 (n = 365) or 0.99727 (n = 366).
- `prcp_seasonality_index`: text says 0 if every month is equal; computed on raw monthly totals, perfectly uniform daily rain gives **0.022374** (non-leap WY) and **0.019126** (leap WY), so a Feb 29 shifts SI by ~0.003.
- `fal` = Oct + Nov (start of the WY) + Sep (end of the WY): non-contiguous, by decision 2 / the Qfal convention.

### 8. NOTE — conventions at the edges

- All-zero year: `prcp_1d_max = 0` but `prcp_max_dowy = 1`; dry run 1…n; `prcp_50_dowy`, `prcp_cm_dowy`, `prcp_gini`, `prcp_seasonality_index`, `prcp_annual_cv` NaN. Never occurs: 0 site-years with zero annual P and 0 without a dry day (fewest dry days in any calendar site-year: 20) in the 368,598 complete calendar site-years. So `prcp_intermit_annual_dowy_start/_end` is never NaN in practice, and leaving it outside the decade gate (decision 14 names only frost) is safe.
- A gage with no PPT-valid year gets **no** `prcp_*` keys (the runner sets `gage_has_climate = false`), whereas a gage with TMIN/TMAX but no temperature-valid year gets the full 19×16 NaN key set. After the runner's union both are empty/NaN columns, but in the CSV the cells are `missing` vs `NaN`.
- The legacy filtering path (`CFG_USE_LEGACY_FILTERING = true`) passes neither `climate_data` nor `temp_data`, so it silently emits no climate columns. Shipped config is `false`.
- The precipitation family has no fallback to `gage_data` (revision 2 removed it), unlike the Q-to-PPT families (`signatures.jl` Q-to-PPT block `cdata = climate_data !== nothing ? climate_data : gage_data`). Correct for the new family; inconsistent between families.

### 9. NOTE — standing hazards and packaging, relevant to the rerun

- Season months: `climate.jl` reads `CFG_NA_SEASON_MONTHS` (config); `flow_volumes.jl:58-63` and `pulses.jl:8` hard-code the same sets. They agree only while the config is unchanged.
- `config.jl` has no `include_dependency(_CONFIG_FILE)`, so editing `signatures_config.json` alone does not rebuild the compile cache (known gotcha). The cache matches the shipped JSON today (a9e8ed31, unchanged since 10:53). Keep the wrapper's `CFG_CLIMATE_ENABLED` check before each batch.
- `julia/Project.toml` (12:52) now declares `Printf` with `[compat] Printf = "1.11.0"` while `julia = "1.9"` is still claimed; Printf 1.11 exists only in Julia ≥ 1.11. Use `Printf = "1"` or drop the compat line. Also `[extras]/[targets]` were reordered by Pkg (cosmetic).
